## 1. What v0.30 actually runs (FACT)

- **Kernel.** `VLLM_GDN_DECODE_KERNEL=cuda` (default) → `ops.fused_gdn_decode_post_conv_mtp` →
  `gdn_decode_post_conv_mtp_kernel<float, 3, true>` (fp32 state, 3 v-heads per k-head at TP=2, sigmoid gate).
  Boot log on v0.30: `qwen_gdn_linear_attn.py:528 GDN decode kernel: cuda` (`evidence/u2-v030-default`).
  Its source is byte-identical to the pin's (`work/verify-fact-F08/gdn.cu` == `gdn_pinned.cu`), so **v0.30 does
  not already avoid the extra writes**: grid (request, v-head), 256 threads, one source read from
  `state_indices[req, a-1]`, and inside the token loop a 64 KiB store of the head's state to
  `state_indices[req, t]` for every verify token `t` (SASS: `STG.E.128` ×4 per chunk per token).
- **When it runs.** `_forward_core_fused_norm` uses it only for *pure* spec batches
  (`_can_use_fused_gdn_mtp_decode` and `num_prefills == 0`). Mixed batches go to `_forward_core`: spec rows
  through FLA `fused_sigmoid_gating_delta_rule_update` (reads column `a-1`, writes every column), non-spec
  rows (0-draft decodes are reclassified as prefills) through the chunk kernel reading/writing column 0.
- **Slot scheme.** Prefix caching on ⇒ `mamba_cache_mode='align'`, block 1600 tokens, V2 model runner
  (`Using V2 Model Runner`). Spec window = `block_table[s : s+1+k]`, `s = (seq_len-1) // 1600`
  (`mamba_get_block_table_tensor`). `MambaHybridModelState.preprocess_state` → `precopy_mamba_align_fused_kernel`
  copies `bt[old_s + a-1] → bt[new_s]` when the window crosses a block and resets `num_accepted` to 1;
  `postprocess_state` → `postprocess_mamba_fused_kernel` copies the candidate at `bt[s + bias]` into the
  completed block at every 1600 multiple (the prefix-cache checkpoint). **Both copies read per-position
  candidate states** — the thing lazy commit stops writing.
- **Graphs.** `COMPILATION_CONFIG={"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}`; GDN builder is
  `UNIFORM_BATCH`, so pure-spec uniform steps replay a captured graph: every K3 input must be a persistent
  buffer and the kernel choice must be made before capture.
- **RecoverSSM** (the in-tree deferred commit) is Kimi-KDA only (`config/vllm.py` validator raises for other
  architectures) and commits after sampling: 2 reads + 1 write (F08 remedy (b)).
- **Stock numerics (SASS of the sm_120 cubin in `_C_stable_libtorch.abi3.so`):** fast-math build.
  `FMUL/FADD/FFMA.FTZ`; `__expf` = `FMUL.FTZ x, 1.44269502` + `MUFU.EX2`; `1/x` = `MUFU.RCP` (no refinement);
  `rsqrtf` = `MUFU.RSQ`; `sum/128 + eps` contracted to `FFMA sum, 0.0078125, eps`; dots are per-lane FFMA
  chains from 0 then `SHFL.BFLY 16,8,4,2,1`; `delta = (v - hk) * beta` as `FADD` + `FMUL`; state update
  `FFMA(k, delta, h*decay)`; outputs `F2FP.BF16.F32.PACK_AB` before the gated RMSNorm; `log1pf` is the
  libdevice polynomial.

## 2. Mapping the plan's design onto v0.30

| Plan (§4 K3) | v0.30 reality | K3 as built |
|---|---|---|
| Committed S_c per (request, v-head) | 1+k slots per request per layer; no committed slot | S_c lives in **column 0** of the current window (`bt[s]`) |
| Ring of exact inputs (≈8.1 KiB/token/rank, k shared per k-head) | — | **Exact BF16 inputs** (post-conv k row, v row, raw a, raw b), **per v-head** (516 B/head/token, 12.1 KiB/token/rank): k is duplicated ×3 so a CTA only ever reads/writes its own head's records (no cross-CTA race). 49.5 KiB per layer per request at k=3 |
| Ring in "the column-1 slot, confirm no other reader" | Column 1 **is** read: by the pre-copy at crossings, the checkpoint copy, and FLA in mixed steps | Ring in rows 120–127 of each head's region of `bt[s+1]`; lazy rows never store state there. The readers are neutralised by the boundary rule and the fixup (below) |
| Replay a accepted records, store S_c once, outputs for k+1, append | Kernel reads `num_accepted` from device (async-safe) | Same, one launch per layer: CTA (request, v-head), 4 chunks of 32 V rows, split-lane fp32 tile in registers |
| Flush before 1600-token checkpoint / preemption / prefix copy | Copies are generic byte copies in `mamba_utils.py` (another overlay target) | **No flush kernel in the copy path.** A row runs *eager* (stock layout) whenever a 1600 multiple lies in `[nc+1, nc+2k+1]`, which covers both the checkpoint copy after this step and the pre-copy before the next one (proof below). Preemption on V2 is recompute → a prefill row → headers dropped |
| — | A lazy step can be followed by a mixed step (scheduled asynchronously) | `gdl_fixup` at the top of `_forward_core`: replays pending rings into the exact stock layout (candidate t → column t) before FLA / chunk readers |
| — | Blocks are freed and reused with stale bytes | Header table `int32[num_blocks]` per layer (allocated by the metadata builder): pending count keyed by the column-0 block id. Zeroed for all window columns by every eager row, every materialize, and every prefilling row |
| RecoverSSM hook port | Not applicable (KDA-only, commit-after-sampling) | Not ported; K3 needs no runner hooks |
| Conv prologue folded in, `torch.zeros` removed | — | **Not done** (kept stock `causal_conv1d_update` and `torch.zeros`): value is a few µs, risk is F01-class |

Boundary rule (why no copy ever sees a lazy layout). Let `nc` = computed tokens before step n, `T ≤ k+1`.
The checkpoint copy after step n reads a candidate only if a multiple of 1600 lies in `[nc+1, nc+a] ⊆ [nc+1, nc+k+1]`.
The pre-copy before step n+1 fires only if `(nc+a+T'-1)//1600 > (nc+T-1)//1600`, i.e. a multiple in
`(nc+T-1, nc+a+T'-1] ⊆ [nc+1, nc+2k+1]`. So `lazy ⇔ nc//1600 == (nc+2k+1)//1600` (computed in-kernel from the
persistent `seq_lens`; ≈0.5% of steps at k=3 are eager). A crossing therefore always follows an eager step, and
eager steps zero the headers of all window columns, so the new column 0 never carries a stale header.

## 3. Numerics

- Goal A0 vs the stock CUDA kernel, because T1-B only passes bit-exact levers (session 5,
  `evidence/k-sweep-precision/SUMMARY.md`). The GPU path uses inline PTX `.ftz` for every float op
  (`mul/add/sub/fma.rn.ftz`, `ex2.approx.ftz`, `rcp.approx.ftz`, `rsqrt.approx.ftz`) in the stock SASS order;
  LLVM can neither contract nor reorder them. `log1pf` is libdevice (same polynomial; its three non-FTZ ops
  differ only on subnormal inputs, which `ex2.approx.ftz` never produces). Lane reductions use `tl.reduce`
  over the 32-lane axis; the offline sm_120 compile (Triton 3.7.1 from the image, `GPUTarget("cuda",120,32)`)
  shows `SHFL.BFLY 0x10,0x8,0x4,0x2,0x1` chains, 116 registers, 0 stack. The layout is the compiler's choice,
  so **A0 is enforced, not assumed**: the self-test requires bitwise outputs every step and bitwise committed
  state, else K3 stays off (fail closed). `VLLM_QWEN38_GDN_LAZY_RED=1` switches to an explicit split-tree
  reduction (order guaranteed by construction, but 8.4 KB stack / 16k `LDL/STL` on GPU: cross-check only).
- Lazy == eager is by construction: replay and the in-step update call the same jit functions. Proven on CPU.
- **§3a GPU fixes (session 7).** (1) `d = tl.reshape(delta, [BV, 1])` gave a `#linear` layout that Triton propagated
  into the updated tile, so the output dot's `tl.reduce` ran register-sequentially instead of `shfl.bfly`: 1-bf16-ulp
  misses on ~1 output in 10^4 (state stayed exact; 2154 spilled registers). `tl.expand_dims(delta, 1)` keeps the
  tile's blocked layout: bitwise, 0 spills. (2) At 8 warps the gated-RMSNorm epilogue had a WAR race (a warp stored
  y over raw o that another warp had not yet loaded: max 1000-ulp misses at c=8); a `debug_barrier` before the
  store fixes it; the same barrier guards materialize's t=0 store over the tile it loaded. Tiling is now
  **BV=64, 8 warps** (c1 32.1 vs 38.8 µs/layer stock; BV=32/4 warps was +0.07 ms/step at c1, failing gate 4).
- If the GPU self-test fails on bits, K3 is class A at best and must go through T1-A + T1-D + T1-G (plan);
  with T1-B saturated that means it would not ship in the default.

## 7. Open items / residual risks

- Builder hunk runs only on GPU boots: `cache_config.num_gpu_blocks` must be set in the worker before the GDN
  builder is created (else `lazy_hdr` stays None and K3 stays off — safe), and the header table must cover
  `kv_cache[1].shape[0]` (checked per call).
- `gdl_layer_init` self-tests at layer construction (inside the model-loader cuda device / bf16 default-dtype
  context; the test pins cpu/fp32 generation explicitly). If the runtime variant key (G, gate, dt_bias dtype,
  norm dtype) differs from the tested one, K3 logs `inactive` and the stock kernel runs.
- INFERENCE, unverified: in stock v0.30 a running request that gets a 0-draft row after a spec step with a>1 is
  read from column 0 (candidate 0), not column a-1. K3's materialize reproduces the stock layout exactly, so it
  neither fixes nor worsens this; worth a separate check.
- Not handled: `mamba_cache_mode='all'` (K3 stays off), bf16 SSM state (off), W > 8 (off), ROCm/XPU.
